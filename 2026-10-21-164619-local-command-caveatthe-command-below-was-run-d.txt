  AI-assisted coding round · Backend (Node.js/Java/Python and  SQL)             
                                                                                
  You are building a coupon redemption service for an e-commerce checkout.      
  Each coupon has: code, max_redemptions (total times it can ever be used,      
  ever), discount_percent, expires_at, and type (STANDARD or STACKABLE). Rules: 
  A coupon cannot be redeemed more than max_redemptions times — even under a    
  burst of simultaneous checkouts on a flash-sale coupon.                       
  A STANDARD coupon can only be redeemed once per customer_id, ever.            
  A STACKABLE coupon (e.g. referral codes) has no per-customer limit, but still 
  respects max_redemptions globally.                                            
  A coupon redeemed after expires_at must be rejected — but a redemption in     
  flight at the exact expiry instant must resolve consistently, not by luck of  
  thread scheduling.                                                            
  Orders can be cancelled. Cancelling an order that used a coupon must give the 
  redemption slot back (redeemed_count decrements) — but only once per order,   
  even if the cancellation endpoint is                                          
  called twice.                                                                 
  Retrying the same redemption request (network client retries after a timeout, 
  doesn't know if the first one landed) must not double-redeem. Callers send    
  an Idempotency-Key header on POST /redeem.                                    
  API:                                                                          
  POST /coupons → { code, max_redemptions, discount_percent, expires_at, type } 
  — seed data.                                                                  
  POST /redeem (header: Idempotency-Key) → { code, customer_id, order_id } → {  
  success: true, remaining } or a clear, distinct error per failure mode        
  (already used / no redemptions left / expired / unknown code / idempotency    
  replay).                                                                      
  POST /orders/:order_id/cancel → reverses the coupon redemption tied to that   
  order, if any. Calling it twice must be a no-op the second time, not a double 
  refund of the slot.                                                           
  GET /coupons/:code → { redeemed_count, remaining, max_redemptions } — this    
  number must be correct at all times, not eventually correct.

     Coupon Redemption Service — Final Plan

     Context

     This is an AI-assisted backend coding round: build a coupon redemption
     service for e-commerce checkout, starting from an empty directory
     (/Users/apple/yellow). The grade depends on correctness under concurrency
     (flash-sale bursts, per-customer limits, consistent expiry, cancels that
     run only once, retry-safe idempotency), and also on production qualities:
     rate limiting, caching, fail-safety, duplicate handling and upserts.

     Stack (decided): Python 3 + FastAPI, PostgreSQL 16 (the only datastore; no 
     Redis), docker-compose, psycopg 3 async + psycopg_pool, raw SQL (no ORM, so
     locking stays explicit), pytest + httpx, Makefile for every workflow.

     Core principles
     1. Postgres alone decides correctness. Each invariant is enforced in one
        transaction, using row locks, unique constraints, CHECK constraints and
        the DB clock.
     2. The cache is only an accelerator (in-process, metadata only). The rate 
        limiter is a Postgres table written with an upsert. If either one fails,
        the service stays correct.
     3. Fail closed on money. If the DB can't confirm a redemption, it is never
        granted. Every error path either commits the full result or rolls back
        to nothing, so there are no partial states.

     ---

     Data model (app/schema.sql, applied idempotently on startup with CREATE ...
     IF NOT EXISTS)

     coupons (
       code             text PRIMARY KEY,          -- normalised: trim + UPPER, 
     so 'save10' == 'SAVE10'
       type             text NOT NULL CHECK (type IN ('STANDARD','STACKABLE')),
       max_redemptions  int  NOT NULL CHECK (max_redemptions > 0),
       redeemed_count   int  NOT NULL DEFAULT 0,
       discount_percent numeric(5,2) NOT NULL CHECK (discount_percent > 0 AND
     discount_percent <= 100),
       expires_at       timestamptz NOT NULL,
       version          int  NOT NULL DEFAULT 1,   -- bumped on every upsert; 
     used as the cache key version
       created_at / updated_at timestamptz,
       CHECK (redeemed_count >= 0 AND redeemed_count <= max_redemptions)   -- 
     DB-level last line of defence
     )

     redemptions (
       id bigserial PK, coupon_code text FK, coupon_type text, customer_id text
     NOT NULL,
       order_id text NOT NULL UNIQUE,              -- one coupon per order; 
     duplicate orders rejected by the DB
       status text CHECK (status IN ('ACTIVE','CANCELLED')),
       redeemed_at timestamptz NOT NULL, cancelled_at timestamptz
     )
     CREATE UNIQUE INDEX uq_standard_once_per_customer
       ON redemptions (coupon_code, customer_id) WHERE coupon_type = 'STANDARD';

     idempotency_keys (
       key text PRIMARY KEY, request_hash text NOT NULL,
       response_status int NOT NULL, response_body jsonb NOT NULL,
       created_at timestamptz DEFAULT now()
     )

     rate_limits (                                 -- fixed-window counters, 
     maintained by upsert
       bucket text PRIMARY KEY,                    -- e.g. 'redeem:cust:C1', 
     'ip:1.2.3.4'
       window_start timestamptz NOT NULL,
       hits int NOT NULL
     )

     Duplicate handling: one layer per kind of duplicate

     ┌───────────────────────────┬─────────────────────────────────────────────┐
     │         Duplicate         │                    Guard                    │
     ├───────────────────────────┼─────────────────────────────────────────────┤

     │                           │  upsert), plus code normalisation           │
     ├───────────────────────────┼─────────────────────────────────────────────┤

     │ concurrent retries        │ response                                    │
     ├───────────────────────────┼─────────────────────────────────────────────┤
     │ Same key, different body  │ request_hash mismatch → 422                 │
     │                           │ IDEMPOTENCY_KEY_REUSED                      │
     ├───────────────────────────┼─────────────────────────────────────────────┤

     ├───────────────────────────┼─────────────────────────────────────────────┤

     │ Double cancel, including  │ conditional UPDATE ... WHERE                │

     │                           │ no-op                                       │

     Endpoints

     POST /coupons: an upsert

     INSERT INTO coupons (...) VALUES (...)
     ON CONFLICT (code) DO UPDATE SET
       discount_percent = EXCLUDED.discount_percent,
       expires_at       = EXCLUDED.expires_at,
       max_redemptions  = EXCLUDED.max_redemptions,
       version          = coupons.version + 1, updated_at = now()
     WHERE coupons.type = EXCLUDED.type                       -- type can't 
     change after creation
       AND EXCLUDED.max_redemptions >= coupons.redeemed_count -- can't shrink 
     below slots already used
     RETURNING *, (xmax = 0) AS inserted;
     - 201 when created, 200 when updated. If no row comes back, the WHERE guard
       failed → 409 COUPON_CONFLICT with the reason.
     - Re-sending the same seed is harmless, so the call is idempotent by
       nature.
     - After commit, the cache entry for the code is invalidated.
     - Pydantic validation: timezone-aware expires_at, type enum, numeric ranges
       → 422.

     POST /redeem: one transaction, READ COMMITTED

     0. Middleware: request-ID, rate limit (see below), missing Idempotency-Key
        → 400 IDEMPOTENCY_KEY_REQUIRED. The body is validated and the code
        normalised.
     1. INSERT INTO idempotency_keys ... ON CONFLICT (key) DO NOTHING RETURNING 
        key.
        - Concurrent same-key requests block on the unique index until the first
          one commits. That gives in-flight dedupe with no extra state machine.
        - On conflict: same hash → replay the stored status and body with
          Idempotent-Replayed: true / "replayed": true. Different hash → 422 
          IDEMPOTENCY_KEY_REUSED.
     2. SELECT *, now() AS evaluated_at FROM coupons WHERE code=$1 FOR UPDATE.
        This row lock serialises redemptions of one coupon. No row → 404 
        UNKNOWN_COUPON.
     3. Expiry: now() >= expires_at → 410 COUPON_EXPIRED. Postgres now() is the
        transaction start time on one clock (the DB's), so the decision doesn't
        depend on lock wait time or on any app server's clock. The exact instant
        counts as expired. The same timestamp is stored as redeemed_at, so the
        decision can be audited.
     4. Capacity: redeemed_count >= max_redemptions → 409 NO_REDEMPTIONS_LEFT.
     5. INSERT into redemptions inside a SAVEPOINT. A unique violation maps to
        ALREADY_REDEEMED_BY_CUSTOMER or ORDER_ALREADY_HAS_COUPON. Then UPDATE 
        coupons SET redeemed_count = redeemed_count + 1.
     6. UPDATE the idempotency row with the final response (success or business
        error) → COMMIT.
        - Infrastructure failures (timeouts, DB down) roll back everything, key
          included, and return 503 RETRYABLE with Retry-After. A retry is then
          safe because nothing landed.

     Success: 200 { success: true, code, order_id, discount_percent, remaining 
     }.
     Errors (uniform): { success: false, error: { code, message, request_id } }.
     Precedence: UNKNOWN → EXPIRED → NO_REDEMPTIONS_LEFT → ALREADY_REDEEMED /
     ORDER_ALREADY_HAS_COUPON.

     POST /orders/:order_id/cancel: one transaction

     1. Look up coupon_code by order_id. No row → 200 { released:false, 
        reason:"NO_COUPON_ON_ORDER" }.
     2. SELECT ... FROM coupons WHERE code=$c FOR UPDATE. This uses the same 
        lock order as redeem (coupon, then redemption), so the two paths can't
        deadlock.
     3. UPDATE redemptions SET status='CANCELLED', cancelled_at=now() WHERE 
        order_id=$1 AND status='ACTIVE' RETURNING id.
        - 1 row → decrement redeemed_count → 200 { released:true, remaining }.
        - 0 rows → 200 { released:false, reason:"ALREADY_CANCELLED" }. Calling
          cancel twice, even concurrently, is a no-op the second time.

     GET /coupons/:code

     - redeemed_count and remaining are always read from Postgres, from the same
       row the redeem transaction updates, so the numbers are exact at every
       moment.
     - Static fields (type, discount, expires_at, max) come from the cache when
       available.
     - 404 if the code is unknown.

     GET /healthz (liveness) and GET /readyz (DB reachable)

     ---

     Caching (in-process, cache-aside, no Redis)

     - What's cached: coupon metadata only (type, discount, expires_at, max,
       version), in an in-process TTL dict (app/cache.py, 30s TTL,
       size-bounded).
     - What's never cached: redeemed_count and remaining. The brief requires
       "correct at all times", and any cached counter has a stale window. A PK
       read in Postgres is cheap. The README will state this trade-off.
     - Where it's used: only for the static fields of GET /coupons/:code. POST 
       /redeem never consults the cache, because it must lock the row in the DB
       anyway, so a cache adds no safety there and only adds risk.
     - Invalidation: after an upsert commits, the code's entry is evicted. With
       multiple instances, another instance's static fields can be stale for up
       to the 30s TTL. The counts are always live, and a production system would
       add LISTEN/NOTIFY invalidation.

     Rate limiting (Postgres, fixed window via upsert)

     INSERT INTO rate_limits (bucket, window_start, hits) VALUES ($1, now(), 1)
     ON CONFLICT (bucket) DO UPDATE SET
       window_start = CASE WHEN rate_limits.window_start < now() - $window THEN
     now() ELSE rate_limits.window_start END,
       hits         = CASE WHEN rate_limits.window_start < now() - $window THEN
     1 ELSE rate_limits.hits + 1 END
     RETURNING hits, window_start;
     - The statement is atomic and works across instances. It runs in its own 
       short transaction before the redeem transaction.
     - POST /redeem: per customer_id (default 10 / 10s) and per client IP
       (default 100 / 10s). Other endpoints: per IP.
     - Over the limit → 429 RATE_LIMITED with Retry-After. It is not stored
       under the idempotency key, so a later retry with the same key works.
     - Configurable through env, and RATE_LIMIT_ENABLED=false for burst tests.
       If the limiter query itself errors, it fails open and logs a warning.

     Fail-safety

     - Atomic transactions: each write is all-or-nothing, and the CHECK and
       UNIQUE constraints back up the app logic.
     - Timeouts: Postgres statement_timeout=3s and lock_timeout=2s (a request
       stuck behind a hot-row lock fails fast instead of piling up); a pool
       checkout timeout. All of these map to 503 RETRYABLE with a rollback, so
       retrying with the same Idempotency-Key is safe.
     - Bounded internal retry: deadlock or serialization errors (40P01/40001)
       are retried up to 3× with jitter, inside the server.
     - Fail closed: if the DB is unavailable, the redeem is rejected (503),
       never optimistically granted.
     - Global exception handler: there are no stack-trace leaks, every response
       carries a request_id, and logs are structured JSON.
     - Startup: wait-for-DB with backoff; schema is applied idempotently.
       Shutdown is graceful: the pool drains on lifespan exit.
     - A docker-compose health check on db.

  How each rule is enforced:
  - Never more than max_redemptions: each redeem locks the coupon's row (SELECT 
    … FOR UPDATE). A database CHECK constraint backs this up. Tested with 200
    checkouts at once on a coupon with 10 slots: exactly 10 succeed and GET
    shows 10 used, 0 left.
  - STANDARD once per customer: a unique index in the database rejects a second
    use, even when two requests race. 50 simultaneous tries by one customer give
    1 success.
  - Expiry at the exact instant: the decision uses the database's clock, read
    once when the request's transaction starts. Waiting for the lock doesn't
    change the outcome, and the expiry instant itself counts as expired. A test
    fires requests while the coupon expires and checks that nothing was accepted
    at or after expires_at.
  - Cancel only once: the slot is given back only if the redemption was still
    active. 20 simultaneous cancels of one order free the slot once.
  - Retries: the Idempotency-Key is stored in the same transaction as the
    redemption. A duplicate request waits for the first, then gets the original
    response back. 50 simultaneous requests with the same key produce 1
    redemption.
  - Upsert: POST /coupons creates (201) or updates (200). Changing a coupon's
    type, or lowering max_redemptions below what's already used, returns 409.
  - Rate limiting: a counter table in Postgres, written with an upsert. Limits
    are per customer and per IP, returning 429 with Retry-After. If the limiter
    itself breaks, requests are allowed through rather than blocked.
  - Caching: only fields that rarely change are cached, and each entry is
    checked against the coupon's version number, so a stale entry is never
    served. Counts are never cached, because the brief requires them to be
    exact.

    nothing is saved, so a retry with the same key is safe. Deadlocks are
    retried up to 3 times inside the server. If the database can't confirm a
    redemption, it is refused, never granted.

  Case 2: both requests hit the DB at the same time

  How the test guarantees it: a separate database session holds a lock on the
  coupon's row. The test then sends requests to both app instances and waits
  until Postgres's own activity view (pg_stat_activity) shows every transaction 
  blocked inside the database at the same moment. It also checks that each one
  is waiting on that lock, directly or behind another waiter. Only then does it
  release the lock.

  What Postgres does next:
  - Two checkouts for the last slot: the first transaction locks the row,
    counts, inserts, and commits. The second was queued behind it, and once
    unblocked it reads the newly committed count, sees 0 left, and gets
    NO_REDEMPTIONS_LEFT. Tested with one request per instance for the last slot
    (exactly 1 wins), and with 36 queued transactions for 5 slots (exactly 5
    win).
  - Same Idempotency-Key on both instances: the retry is blocked by the
    original's uncommitted key row. When the original commits, the retry replays
    its response, so the customer is charged once.
  - Double cancel on both instances: the second cancel re-checks the order's
    status after the first commits, finds it already cancelled, and does
    nothing.
  - Without the app at all: two raw SQL transactions try to go past the cap, or
    insert the same STANDARD customer. The second waits, then is rejected by the
    database's CHECK and UNIQUE constraints, so the schema on its own refuses.

  Case 1: the DB crashes

  One session dies mid-transaction. I kill the app's database session after it
  has claimed the idempotency key but before it commits:
  - The client gets 503.
  - Everything is rolled back: no key, no redemption, no count change.
  - A retry with the same key succeeds, and that app instance keeps serving.

  The whole Postgres server is killed. The test sends SIGKILL to the container
  while 400 redeems are in flight on both instances, then restarts it. Across
  the runs, about 20 had been confirmed and about 380 were in doubt each time:
  - While the DB is down: /redeem returns 503 RETRYABLE, never a guessed
    success, and both /readyz return 503.
  - Durability: every redemption a client was told succeeded is still on disk
    after recovery.
  - Atomicity: after recovery, the count still equals the active redemptions,
    and nothing half-written survived.
  - Recovery: both apps reconnect on their own. Clients retry the in-doubt
    requests with the same keys, and the coupon ends at exactly 150/150 with
    nothing charged twice.

  One window the crash never happened to hit: the DB commits but dies before the
  client gets the response. The retry would then replay the saved response
  rather than charge again. The test counts this case, but it came out 0 in
  every run. The same-key replay logic itself is covered deterministically by
  the gate test above.

    connection is dead, so the pool now replaces them instead of failing the
    first requests.

    apart.

      113 +**Redeem** is one transaction with two phases:                
      114  
      115 +1. **Claim the Idempotency-Key** with `INSERT … ON CONFLICT DO
          + NOTHING`. If the same key is already in flight on any instanc
          +e, this insert *waits* until that transaction finishes, then r
          +eplays its stored answer.                                     
      116 +2. **Phase 1, no lock.** Read the coupon and check: unknown, e
          +xpired, STANDARD customer already used it, order already has a
          + coupon, sold out. Each of these answers is final for this req
          +uest, so it is returned immediately. Rejected requests **never
          + queue on the hot row**, which matters most once a flash sale 
          +sells out.                                                    
      117 +3. **Phase 2, row lock.** `SELECT … FOR UPDATE` on the coupon.
          + This serialises every grant for that coupon across all instan
          +ces. The usage checks are then **re-run in a new statement**: 
          +in READ COMMITTED, a statement only sees rows committed before
          + it started, so this is how it sees the redemption committed b
          +y the transaction it was queued behind. The count is re-checke
          +d under the lock.                                             
      118 +4. Insert the redemption, increment the counter, and store the
          + response under the key, all in the same commit. If anything f
          +ails, everything rolls back, including the key.

      134 +|---|---|                                                     
      135 +| **Bulkhead**: at most 8 in-flight redeem transactions per co
          +upon per instance (`REDEEM_MAX_INFLIGHT_PER_COUPON`) | A hot c
          +oupon can't occupy the whole connection pool and starve other

          -K and UNIQUE constraints behind the app logic.

          -k behind a hot-row lock fails fast with `503 RETRYABLE` instea
          -d of piling up. The pool checkout timeout returns 503 the same
          - way.

          -p to 3× with jitter.

          -s never granted.                                              
      162 -- No stack traces leak, and logs are structured JSON with a re
          -quest id.                                                     
      163 -- Startup waits for the DB and runs migrations under an adviso
          -ry lock. Shutdown drains the pool.
